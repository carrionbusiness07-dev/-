# Состояние проекта «Хроника»

Обновлено 31.10.2026. Первый файл для новой сессии Claude: что уже работает, что отложено, о чём договорились.

## Что работает

- **Сбор** с четырёх площадок, все проходят выдачу целиком (24.10, около 00:30):

  | Площадка | Объявлений | Как часто | Особенности |
  |---|---|---|---|
  | Kufar | ~11 850 | 30–60 мин | Только с белорусского IP. Адрес в поле `v` (до 23.10 читался пустой `vl`, объявления пересклеены командой `relink-unaddressed`) |
  | Realt | ~6 500 | 30–60 мин | Сам отдаёт направление последнего изменения цены (`priceChangeDirection`) |
  | Onliner | ~1 150 | 30–60 мин | Только свои объявления: копии Realt (фото на `files.realt.by`) пропускаются |
  | Domovita | ~2 900 | раз в 6 ч | Отдаёт историю цены. Платные объявления повторяются на каждой странице, поэтому страниц больше расчётных; 404 за последней страницей означает конец выдачи |

- **Отделка** (с 24.10): Kufar `flat_repair` → `extra.flat_repair` + подпись `extra.repair`, Realt `repairState` (подписи из данных Realt, `REALT_REPAIR_LABELS`). Если значимые поля снимка не изменились, а `extra` изменился, `extra` последнего снимка обновляется на месте (без нового снимка).
- **Хеши фото** (с 24.10): первые 6 ссылок на фото хранятся в `extra.photo_urls`; после прохода площадки и до склейки сборщик скачивает до 6 фото на объявление (не склеенные → low → их двойники → новые), считает phash и выбрасывает картинку. Бережно: до 150 фото и 5 минут на площадку за проход, один запрос за раз, пауза 1–2 с, остановка после трёх отказов (алерт) или трёх сетевых ошибок подряд. Выключить: `PHOTO_HASHING=0` в `.env`, затем `docker compose up -d collector` (простой `restart` `.env` не перечитывает). Очередь (~8 тыс. объявлений) разбирается несколько дней.
- **Детали и факты из описания** (с 31.10): Kufar, Realt, Domovita пишут в `extra` кухню, жилую площадь, потолки (Kufar «от …»), санузел, балкон, стены (только Kufar `house_type`), окна, обмен и `facts` — коды фактов из описания продавца (`analytics/facts.py`, словарь правил с отрицаниями). **Текст описания не хранится**: факты извлекаются в `to_raw`, текст удаляется из payload. Kufar отдаёт только первые 150 символов описания, Onliner — без описаний. Первый проход Kufar 31.10: санузел у 6,7 тыс. объявлений, кухня у 2,8 тыс., факты у 3,5 тыс.
- **Склейка** дублей между площадками и событий: исходный срез первых суток не считается «новым»; события по квартирам из среза пишутся без уведомлений.
- **Кабинет** на `http://localhost:8080`: «Что изменилось» (лента по 50 строк, полоса «Ход наблюдения»), «Объекты» (по 100), «Рынок», «Источники» (причины ошибок, «прерван»). Срез рынка кэшируется и пересчитывается в фоне после каждого прохода.
- **Оценка квартиры** в `/check` и на странице квартиры в кабинете (с 24.10, спека `docs/superpowers/specs/2026-10-24-flat-assessment-design.md`): вывод наверху («Стоит смотреть» / «Цена в рынке» / «Дороже похожих» / «Подозрительно дёшево»), сравнение цены за м² с похожими квартирами (комнаты, эпоха дома, отделка, 1,5 → 3 км → район), метро в минутах пешком, детали и факты из описания, «Ещё в этом доме». С 31.10 минусов, плюсов и вывода о торге нет (решение владельца), у новостроек нет «подозрительно дёшево» — вместо него «Стоит смотреть» (`is_new_building`); на 31.10 «подозрительно дёшево» — 8,4% квартир. С 30.10 в шапке метка «новостройка / вторичка, дом … г.» (флаг Kufar `flat_new_building` и год постройки); блок «Кому подойдёт» убран по решению совета. В кабинете карта (Leaflet + OpenStreetMap) с квартирой, метро и похожими квартирами; бот после отчёта присылает точку на карте. Статистика по всему рынку: `python -m minsk_realty.analytics assessment`.
- **Страница квартиры в кабинете** (с 25.10): фото квартиры прямо с площадки (до 6, просмотр крупно; у нас не хранятся; с 31.10 больше не обрезаются), карта на приглушённой подложке OSM с кликабельными ярлыками цен похожих квартир (▼ дешевле / ▲ дороже, группировка в плотных местах, не больше 300 ближайших групп), лента событий вместо пустого графика при короткой истории, история цены «со слов площадки» (Domovita, Realt), таблица площадок с адресом, этажом, площадью и фото. CARTO не используем — требует ключ.
- **Районы по координатам** (с 30.10): Realt и Onliner района не отдают (~3,3 тыс. объектов были без района). Теперь район определяется по точке квартиры по границам 9 районов из OpenStreetMap (`analytics/minsk_districts.json`, скрипт `scripts/fetch_minsk_districts.py`, `district_at`), в базу не пишется. Фильтр районов на «Объектах» — 9 чистых названий.
- **Поиск квартир в боте** (с 31.10, спека `docs/superpowers/specs/2026-10-30-flat-search-design.md`): `/search` или кнопка «🔍 Найти квартиру» — анкета в одном сообщении (бюджет, комнаты, районы, площадь, новостройка/вторичка, этаж), выдача по 5 карточек со всех площадок, каждая квартира один раз, сначала выгодные (ещё «дешёвые», «свежие»), превью ссылки площадки вместо наших фото, «Подробно», «Следить», подсказки при пустой выдаче, повтор прошлого поиска. Индекс (~15 тыс. квартир, ~80 с) бот пересчитывает в фоне, проверяя новые данные раз в 15 минут; пока считает — отвечает по прошлому. Память бота после пересчёта ~506 МБ (было ~310). Таблицы `saved_searches`, `search_shown` (миграция 0005), `/forget` стирает и их.
- **Telegram-бот**: `/check` по ссылке любой из четырёх площадок, «Следить», `/list`, уведомления, недельная сводка. После любого отчёта (ссылка, `/check`, кнопка «Отчёт») — место на карте с подписью; для неточных координат Realt/Domovita — «≈ … (примерно)».
- **Надёжность**: ежедневный бэкап в `D:\minsk-realty\backups` (14 дней); алерты в Telegram; внешний сторож healthchecks.io (`HEALTHCHECK_URL` в `.env`: проверить, задан ли); автозапуск Docker Desktop. 30–31.10 Docker трижды останавливался (место на C; выход из сна при нехватке памяти; ночь 30→31.10 — Docker Desktop не запущен, ~14 ч, причина не найдена) — ноутбук на зарядке не должен засыпать, файл подкачки лучше перенести на D; сторож, перезапускающий Docker, предложен владельцу, ждёт его решения.

## Договорённости

- Аренду как отдельный продукт не делаем. Масштабирование — после первых платящих.
- Крупные изменения перед выкаткой проверяет агент Grant (`grant-guard`). Так нашлись ложные события на Onliner/Domovita до того, как они попали на домашний ПК.
- Решения по продукту — через llm-council, когда владелец просит.
- Пороги групп оценки (−25% «подозрительно дёшево», ±10% «в рынке») владелец выбрал 24.10 по живым данным, а не заранее (спека, раздел 10): «подозрительно дёшево» — 9,1% квартир. Неточные координаты считаются у Realt и Domovita (`approx_coord_sources`, проверка 24.10: доля общих точек 10,1% и 26%) — для их квартир нет карты и минут до метро, цена сравнивается с районом.
- Персональные данные продавцов (телефоны, имена, id аккаунтов, реквизиты) не попадают ни в базу, ни в фикстуры.
